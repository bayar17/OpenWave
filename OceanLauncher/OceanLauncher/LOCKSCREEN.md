# Ocean lock screen

Ocean owns the lock controller in the compositor process. `LockController` keeps the authoritative state in C++, and `LockScreen.qml` is a presentation layer above the launcher and Wayland application surfaces. While locked, Ocean disables surface input, navigation gestures, keyboard shortcuts, Quick Menu access, and prompt presentation. Existing application processes and surfaces remain alive behind the lock layer.

The controller atomically records `locked` in `/run/openwave/ocean-lock-state` with owner-only permissions. A launcher restart in the same boot therefore restores the locked state; an invalid state file also fails closed. `/run` is temporary storage, so this first version does not claim to provide secure boot-time locking. The setting is a session lock request from Quick Menu, not display sleep or suspend.

The current completion flow is deliberately labeled **Lock Screen UI / Development Preview**. A sufficiently long upward swipe from the lower screen starts the development-only unlock path. It is not credential authentication and must not be represented as a secure device lock. A future credential backend must authenticate in a trusted service, protect a password hash, throttle attempts, and only then authorize the controller to clear the session lock.

Ocean reuses its Inter fonts, wallpaper, status indicators, time source, and Reduce Motion preference. The current system has no battery or charging telemetry API, so the lock screen displays the existing battery glyph only; it does not invent a percentage or charging state. The safe-area inputs are exposed on the reusable QML component and default to the existing 70-pixel status region.

`TileWallpaperItem` decodes the active wallpaper once on a Qt Core worker thread and uploads one scene-graph texture. `TilePuzzleModel` owns a rectangular grid with one vacant cell, starts that cell at the grid center for each lock session, and permits only adjacent horizontal or vertical swaps into it. Later moves can traverse the whole grid. The renderer uses square, clipped cells, one batched scene-graph texture, and UVs fixed to each tile's original wallpaper crop. One tile slides at a time along a straight line; no tile rotates, overlaps another tile, or leaves the grid. Idle moves are paced and avoid immediate reversals. Pointer and touch drags increase activity, prioritize legal movement in the gesture direction, and shorten the delay and slide duration; when that direction is unavailable, the model schedules another legal neighboring move. The original wallpaper remains underneath the clipped tile item, and the vacancy has no tint so aligned tiles and the underlying image retain the same colors. Reduce Motion resets the arrangement to the stationary wallpaper. Animation pauses when the lock surface is hidden or the Qt application is inactive. OpenWave does not currently expose a dedicated display-off event to this component.

The reviewed Plasma Mobile reference at commit `79d525dba45e` includes lock-screen integration through a Wayland lock-screen overlay client extension. That client-side mechanism is not used here: application clients must not be able to request or remove OpenWave's lock. OpenWave instead places the trusted UI in its own compositor and gates application-surface input in the same process.

The tile renderer uses the existing WPE Qt `QQuickItem::updatePaintNode` scene-graph pattern as an in-repository reference. The Plasma review informed only the trusted-overlay ownership boundary; no upstream animation implementation was copied.

## Validation

Run the focused UI tests with:

```sh
QT_QPA_PLATFORM=offscreen QT_QUICK_BACKEND=software \
  toolchain/bin/qmltestrunner -input OceanLauncher/OceanLauncher/tests/tst_lock_screen.qml
```

Build and run the controller persistence tests with the host Qt toolchain:

```sh
cmake -S OceanLauncher/OceanLauncher/tests/lockcontroller \
  -B out/lockcontroller-host -G Ninja -DCMAKE_CXX_COMPILER=/usr/bin/c++
cmake --build out/lockcontroller-host
ctest --test-dir out/lockcontroller-host --output-on-failure
```

This implementation does not change the kernel or production image. The compositor target was installed into a copy of `rootfs`, packed as `out/lockscreen-qa-final.img`, and booted in QEMU at 544x960. A VNC mouse tap opened Quick Menu, selected Lock, and showed the dimmed lock screen; an upward VNC drag completed the development unlock and returned to Home. The guest log confirmed SELinux enforcing and had no AVC-denial lines. The disposable image was repaired and passed offline `e2fsck -fn` after QEMU stopped.

Host validation: the launcher target builds; lock-screen QML tests pass 8/8; Quick Menu tests pass 10/10; and the controller persistence executable passes all 3 behavior cases. The full QML directory run had 76 passing tests and 3 unrelated portal/prompt test load failures because the host runner does not have the `OpenWave.Fonts` QML module installed. The QEMU run verifies the visual lock, mouse gestures, and enforcing boot; controller restart persistence is covered by host tests. The guest was not restarted while locked, so the on-guest persistence round-trip remains to be checked separately.

The Picture Puzzle host test executable passes 8 behavior tests (10 QtTest entries including setup and cleanup), covering grid occupancy, a single vacancy, cardinal moves, gesture-directed scheduling, preservation of an in-flight move while pausing, reduced-motion reset, inactive-window pause and resume, and repeated pointer input. The `appOceanLauncher` target builds successfully and is staged under `rootfs/System/Applications/com.openwave.shell`. A standalone lock-screen QML test run could not load `OpenWave.Shell`, because those C++ types are registered by the launcher executable rather than a standalone QML plugin. `OpenWave.img` and the kernel remain unchanged.

The touch-driven reveal update starts the existing tile renderer as soon as an upward drag from the lower screen becomes active. Its normalized progress follows the pointer displacement (with a display-height-scaled travel distance), and the renderer applies linear vertical movement with a short top-row delay so lower tiles depart first. The initial pointer delta is applied as soon as the drag handler takes the gesture, avoiding a first-frame pause. The same progress fades the lock text and shading. A single batched scene-graph layer draws soft black shadows beneath tile quads only while they are moving. A downward drag reverses the same progress. An incomplete release settles both tile progress and lock-content offset back to zero, then resumes the idle puzzle. An authorized release continues from the held progress; the unchanged wallpaper underlay remains safe until authorization, and OpenWave keeps application input disabled while locked.

Validation for this update: the tile renderer host tests pass 11/11 QtTest entries, including preservation of live progress across `beginReveal()` and reset on cancellation; LockController passes its CTest target; and the `appOceanLauncher` target builds and installs to `rootfs`. In disposable x86_64 QEMU at 544x960, VNC captures at partial, held, reversed, and completed drag positions show tile movement during the gesture, a stable image while held, a restored locked screen after a short swipe, and the authorized return to Home after a full swipe. Host SELinux remained enforcing, and the guest log showed no AVC denial or lock-screen QML error. The standalone QML test runner remains unavailable because it cannot load the app-registered `OpenWave.Shell` module. No kernel changes were made. The disposable image passed `e2fsck -fn` after offline journal recovery.

The wallpaper shading correction replaces the full-screen wash with separate top and bottom gradients inside the lock-content layer. They sit above the wallpaper and tile renderer but below text and icons, fade before the center region, and apply uniformly across tiles. The puzzle vacancy remains transparent. No tile movement, gesture, layout, or unlock code changed in that shading-only update. The launcher was rebuilt and staged, and at that time a fresh `OpenWave.img` was created from `rootfs` because no image existed at the repository root. The image passed `e2fsck -fn`, and its launcher binary was verified. A host pixel comparison was not usable because Qt's offscreen software window returned a white frame instead of rendering the custom scene-graph texture; subsequent visual review on the locked QEMU screen is recorded below.

Puzzle Reveal uses one `revealProgress` timeline after the lock controller authorizes the development unlock. The puzzle model pauses without finishing or resetting an in-flight move; the renderer then moves its existing textured quads upward with a deterministic bottom-to-top stagger and small column offsets. The lock wallpaper fades to the already-running Ocean scene underneath, so the existing home view or foreground application is revealed without a screenshot or relaunch. The UI fades from 30 to about 280 ms, shading from 30 to about 350 ms, and the home dock enters from about 190 to 440 ms. Reduce Motion crossfades the tile and lock layers instead. The lock controller keeps input blocked until the 450 ms reveal finishes. Authentication remains explicitly development-only; no passcode backend is implemented.

The reveal was rebuilt and installed into `rootfs`, then tested in the disposable `out/puzzle-reveal-validation2.img` at 544x960. A VNC lock action and upward swipe showed the staggered tile exit, fading lock UI, and dock entrance before returning to the existing Home scene. The guest boot log confirmed SELinux enforcing and no QML state-handler errors appeared during lock or unlock. Tile-wallpaper host tests passed 10/10 QtTest entries; LockController passed 1/1 CTest target; `appOceanLauncher` built successfully. The disposable image passed offline `e2fsck -fn` after journal recovery. `OpenWave.img` and the kernel were not modified.
